# DSH 每日简报 · 功能设计方案

> 本文是「DSH 每日简报」的完整功能设计稿：在现有插件能力之上，补齐**正文摘要、工具统计、呈现形式、健康建议**四大块，并给出实现路线。
> 前置调研见 [RESEARCH.md](RESEARCH.md)。
>
> **归档说明**：本文写于 2026-11，是开发过程记录，已做路径脱敏。文中「本机」指当时开发者的机器，版本号（如 DSH `0.1.1-rc.2`）为当时实测环境，不保证与当前版本一致；正式对外文档见 [GUIDE.md](../GUIDE.md) 与仓库根 [README.md](../../README.md)。
>
> **文档约定**：所有「能拿到什么数据」的判断，都来自我实际读取本机会话日志（`~/.dsh/sessions/**/session.v4.jsonl.zstd`）的实测结果，不是推测。凡是拿不到的数据，会明确标注「需新采集」。
>
> 背景速览：本机 `@deepseek-ai/dsh` = 0.1.1-rc.2，cordis 4.0.1。现状基础是 `dsh-period-report@0.2.1`（MIT，peer 依赖兼容本机），它已能做「会话日志 → Markdown 工作报告 + AI 叙事 + 定时投递」，但：AI 只吃「标题 + 首条请求前 160 字」、不吃正文；没有天气；没有 Host 启停时间；通知只有 macOS/Linux 分支，Windows 不弹。

## 一、数据基础：日志里到底能拿到什么

以本会话（725 个事件、1.9 MB 解压后文本）为例，逐事件实测结果：

| 事件类型 | 能拿到的字段 | 能支撑的功能 |
|---|---|---|
| `user/message` | 完整正文、`time`、`source.clientTimeZone`、`source.kind`（区分真人 / 注入） | 正文摘要、输入习惯、作息统计 |
| `assistant/message` | 完整正文、`usage`（input/output/cacheRead/cacheWrite/reasoning/total）、**`stream[].time` 流式块时间戳** | token 用量、首字延迟（TTFT）、输出速度 tok/s |
| `tool/call` → `tool/result` | 工具名、**完整 arguments**、`isError`、两端 `time` | 工具统计、耗时、失败率、改了哪些文件 |
| `job/registered` → `job/settled` | 命令原文 `label`、`status`、`detail`（退出码）、`startedAt`/`finishedAt` | 跑了哪些 shell 命令、哪些失败 |
| `approval/asked` → `approval/decided` | 审批原因 `reason`、结果 `outcome`、时间差 | **你被审批打断等了多久** |
| `llm/retry` | 错误分类 `code`、failure 原文、重试次数 | 服务稳定性（本会话实测 3 次 504） |
| `turn/end` | `reason.kind`（completed / interrupted / error） | 任务完成率 |
| `todo/write` | 待办全量列表 + 状态 | 自动生成「明日待续」 |
| `deliverables/presented` | 交付文件路径 + 描述 | 今日产出清单 |
| `workspace/changes` | 轮次号（本会话仅有 turn，内容较少） | 改动概览 |
| `session/title`、`session/title-llm-request` | 会话标题及其来源 | 摘要的标题来源 |

### 拿不到的两样（必须新采集）

1. **dsh 启停时间** —— 日志里没有任何 Host 启动/关闭事件。`dsh-period-report` 现在只有「逐会话活跃时间段」`firstActive ~ lastActive`，这是**会话活跃区间**，不是进程启停。
2. **打字过程** —— 只有「消息发出」的 `time`，没有按键级数据。这直接决定了「用输入间隙反推久坐」这条路是否成立，详见第五节。

### 一个实测反例：为什么不能只看消息间隔

本会话 3 条真人消息，相邻间隔是 **2220 分钟** 和 **5 分钟**。

- 那个 2220 分钟只是「隔了一天多再回来」，不是连续盯着屏幕 37 小时；
- 反过来，如果我在 VS Code 里干了两小时，DSH 一条消息都没有，也不代表我在休息；
- 一条长消息我可能打了 10 分钟，日志只记发出那一刻。

**结论：消息间隔只能说明「DSH 内活跃」，不能说明「人坐在电脑前」。**

## 二、正文摘要：分层摘要，不整段喂模型

### 问题

现有实现把「标题 + 首条请求前 160 字」交给模型，模型写出来的「今日主线」本质是**复述意图**，不是**交代结果**。用户看日报想知道的是「这事做成了没有」，不是「我早上想干什么」。

### 改法：两层流水线 + 缓存

```
会话原始事件
   ↓  代码压缩（确定性，不花 token）
「事实包」（约 2~4k token/会话）
   ↓  便宜模型写 1~2 句
每会话一句话摘要（缓存：按 sessionId + 最后事件 seq 做键）
   ↓  再次汇总
当日 3~5 条回顾
```

### 事实包里放什么

只放高价值信息，宁缺毋滥：

| 内容 | 取法 | 理由 |
|---|---|---|
| 全部用户消息原文 | `user/message` 且 `source.kind === 'user'` | 这是「意图」，最不能省 |
| **每轮最后一条助手回复** | `assistant/message`，按 turn 分组取末条 | 这是「结论」，比中间过程重要 |
| 改动的文件清单 | `tool/call` 里 `name in (edit, write, str_replace…)` 的 `file_path` | 回答「动了什么」 |
| 失败的工具与命令 | `tool/result.isError === true`、`job/settled.status !== 'completed'` | 回答「卡在哪」 |
| 未完成的 todo | 最后一次 `todo/write` 里 `status !== 'completed'` | 回答「明天接着做什么」 |

**不放**：完整工具输出（噪音大、token 高）、中间推理文本、会议式寒暄。

### 提示词约束

要求只输出 1~2 句，且必须是「**做了什么 + 结果如何**」的句式：

> ✓ `检索 DSH 插件市场的每日简报插件；结论是没有五项全覆盖方案，最接近的是 dsh-whale-report，已输出对比报告。`
> ✗ `用户想找每日简报插件，我进行了检索。`（只有过程没有结论）

### 缓存是成本关键

昨天的会话不会再变。摘要生成一次后落盘，第二天只对新会话花钱。缓存键 = `sessionId + 最后事件 seq`，seq 变了才重算。

**成本估算**：假设一天 8 个会话、每会话事实包 3k token、模型输出 60 token，则摘要阶段约 24k 输入 + 0.5k 输出。按 DeepSeek 谷时价粗算，一天几分钱到一两毛钱量级 —— 比用户自己翻日志省得多。

## 三、工具统计：比「次数」更有用的维度

只统计调用次数价值有限。下表是建议纳入的维度，全部可由现成日志算出：

| 维度 | 数据来源 | 为什么有用 |
|---|---|---|
| 调用次数排行 | `tool/call.name` 计数 | 基础信息，看主力工具 |
| **失败率** | `tool/result.isError` / 总数 | 哪个工具老出错，可能需要换用法 |
| **耗时分布** | `tool/call.time` → `tool/result.time` 差值，取 p50 / p90 | 时间花在哪，慢工具优化 |
| **命令分类** | `job/registered.label` 按前缀归类：`git` / `npm` / `node` / `python` / `pwsh` / 其他 | 今天主要在做哪类活 |
| **改动文件热度** | `edit`/`write` 的 `file_path` 计数 | 同一文件改了 9 次 = 反复折腾，值得复盘 |
| **访问的网站** | `web_fetch` / 搜索类工具 arguments 里的 URL 取域名 | 查了哪些资料 |
| **审批等待** | `approval/decided.time − approval/asked.time` 求和 | 「你被打断几次、总共等了多久」 |
| **输出速度** | `assistant/message.stream` 首尾时间戳 + `outputTokens` | 模型侧性能，辅助判断是否卡顿 |

### 呈现建议

工具统计不要单独占一大块，**挂在「工具与产出」小节**里，用一张紧凑表格 + 一个「异常项」列表：

```
Top 工具    pwsh×38  read×21  write×12  webfetch×9  grep×6
耗时榜      pwsh p50 4.2s / p90 61s   ·   webfetch p90 28s
失败        3 次：pwsh×2（exit 1）· write×1（路径不存在）
改动最多    src/index.js ×9  ·  README.md ×4
命令构成    git 12 · npm 8 · node 15
审批等待    2 次，合计 1.5s
```

## 四、报告呈现：分三层，不同时间读不同深度

### 核心原则

**同一份数据，三种阅读深度。** 早晨只想看 30 秒，复盘时才展开细节。不要把 20 个指标平铺成一个长列表 —— 那种报告用户第三天就不打开了。

### 版式草图

```
┌────────────────────────────────────────────────────────┐
│ 11月12日 周三 · 明日 南京 · ☁ 14°C 小雨 · 建议带伞     │  ← 第 1 层：30 秒
│ 今天：dsh 08:52 启动，在线 6h20m                        │
│ 3 个会话 · 105 次工具 · 84 万 tokens（约 ¥1.2）         │
│ 一句话：完成插件调研，开始设计日报功能方案。             │
│ ⚠ 连续 2h10m 未休息 · ⚠ 23:40 仍在工作 · 1.3 亿 ▼ -59% │
├────────────────────────────────────────────────────────┤
│ ▸ 今日主线（每会话 1~2 句）                              │  ← 第 2 层：3 分钟
│ ▸ 用量与成本（含近 7 天对比 ▲▼）                        │
│ ▸ 工具与产出（Top 工具、改动文件、交付物）               │
│ ▸ 卡点（失败、重试、被中断的任务）                       │
│ ▸ 作息与健康                                            │
│ ▸ 明日待续（未完成 todo 自动带过来）                     │
├────────────────────────────────────────────────────────┤
│ ▸ 附录：逐会话明细 / 命令清单 / 原始数据                 │  ← 第 3 层：按需
└────────────────────────────────────────────────────────┘
```

### 形态：一份数据，三种出口

| 出口 | 内容 | 场景 |
|---|---|---|
| **早晨弹出卡片** | 只放第 1 层 | DSH 打开时显示一次，不打扰 |
| **单文件 HTML** | 内联 CSS + 内联 SVG，无脚本无外链；第 2、3 层默认折叠 | 存档、分享给同事（可脱敏） |
| **Markdown 归档** | 全量，落盘 `~/.dsh/…/reports/` | 给 agent 读，方便日后问答「上周我在干嘛」 |

### 写法上的三条规矩

1. **数字由代码算，模型只写文字。** 提示词里把统计数字给定，并明确「不要自己计算、不要四舍五入」。这是防止报告编数据最有效的一条。
2. **只写有变化的内容。** 没有失败就不出现「卡点」段；没有超时就不出现健康提醒；没有未完成 todo 就不出现「明日待续」。**恒定的段落会训练用户忽略整份报告。**
3. **指标必须带参照。** 任何单独的数字（84 万 tokens）都不如带上「较 7 天均值 ▲23%」有意义。

## 五、健康建议：用输入间隙反推久坐靠谱吗

### 结论：单靠 DSH 消息间隙不成立，要换数据源

三种典型误判：

| 场景 | 消息间隔视角 | 真实情况 |
|---|---|---|
| 发完任务去倒水，agent 跑 20 分钟 | 看起来一直在用 | 人站起来了 |
| 在 VS Code / 浏览器干两小时 | 看起来在休息 | 一直坐着 |
| 一条长消息打了 10 分钟 | 只记发出那一刻 | 无法反映节奏 |

### 推荐信号：Windows 全局键鼠空闲时间

Windows 提供 `GetLastInputInfo`，返回「上一次收到键盘/鼠标输入的时间」——**任意程序都算**，且**不记录按了什么键**。

采样逻辑（插件每分钟采样一次）：

```
空闲时长 < 2 分钟   → 判定「在用电脑」
空闲时长 ≥ 5 分钟   → 算一次休息，打断当前「连续段」
连续段 > 50 分钟     → 记一次「久坐段」
```

产出可信度较高的结论：

> 今天用机 7h20m，最长一段连续 **2h10m（14:05–16:15）没有休息**，超过 50 分钟的有 3 段。

隐私上这是最小必要采集：只知道「有没有动」，不知道「动了什么」。

### DSH 自身数据可作辅助（作为佐证，不单独定论）

- **作息**：首次 / 末次活动时刻 → 是否熬夜（如 23:30 后还在发消息）
- **午休**：11:30–13:30 是否持续活跃 → 「中午没离开过」
- **周末**：统计周末工作天数

### 措辞与开关

**只做行为提醒，不做医学判断。** 用「提醒」而非「诊断」：

> ✓ `最长一段 2h10m 没离开键盘，下次试试每 50 分钟起来一下。`
> ✗ `你久坐过度，有腰椎风险。`

健康板块**必须支持一键关闭**，且默认只在检测到异常时才出现（见「只写有变化的内容」）。

## 六、其他可加功能（按价值 / 难度排优先级）

### 高价值、日志现成就有

1. **明日待续** —— 从未完成 todo + 被中断的轮次自动生成，第二天简报开头显示。**最实用的一项。**
2. **成本与省钱建议** —— 缓存命中率、峰谷时段占比（如「60% 用量在高峰期，挪到谷时约省 ¥X」）、最贵的一轮是哪轮。
3. **卡点与摩擦** —— 失败工具、504 重试、被中断轮次、反复改同一文件。比「用了多少 token」更能说明今天哪里不顺。
4. **与近 7 天对比** —— 每个数字标 ▲▼。单独的数字没有参照就没有意义。
5. **返工率** —— 用户消息里出现「不对 / 重来 / 不是这个意思」的比例，反映需求说清程度（需谨慎，只当参考，不评判）。

### 需要新采集

6. **dsh 启停时间** —— 写一个 Host 插件：启动时记录 `bootId` + 时刻，**每分钟写一次心跳**；下次启动时把上次最后一条心跳当作「关闭时间」。
   > ⚠ 不能依赖退出钩子 —— 崩溃、强杀、直接关机时钩子不执行，会永久丢数据。心跳法是唯一稳妥做法。
7. **天气** —— Open-Meteo 免费、无需 key。只在「需要注意」时出声：下雨、降温 >5°C、空气差。可结合作息给一句话（「明早有雨，记得带伞」）。
8. **键鼠空闲采样** —— 即第五节的健康数据源。

### 锦上添花

9. **周报 / 月报** —— 同一套数据换个时间窗口，加「本周主线」「最常改的项目」。
10. **目标与预算** —— 设每日 token 预算或专注目标，简报里显示达成情况。
11. **问答式回看** —— 报告存成 Markdown 后，直接问 agent「上周三我修了什么 bug」。

## 七、实现路线

### 底座选择

`dsh-period-report` 是 **MIT** 协议，peer 依赖（`dsh-tools`/`dsh-system-prompt ^0.1.0-rc.6`、`cordis ^4.0.1`）兼容本机 0.1.1-rc.2，可以直接 fork 改。已知需要补的坑：

- 通知只有 `darwin → osascript` / `linux → notify-send`，**没有 win32 分支**，Windows 上不会弹通知，需自行补 PowerShell Toast 或托盘提示。
- 定时是 `timer.interval` 每 30 秒轮询打点，不是 cron；`intervalDays` 1–90。
- AI 摘要段目前只喂「标题 + 首条请求 160 字」，上限 25 个会话 —— 第一节的摘要改造就替换这里。

### 架构：四层解耦，以后加功能只动一层

```
采集层                    →  当日事实库          →  分析层              →  呈现层
─────────────────────────     ─────────────────      ─────────────────      ──────────────────
会话日志 (sessionQuery)       每天一个 JSON         确定性规则算数字       三层 HTML 卡片
心跳插件 (dsh 启停)           （可增量、可重算）     模型只写摘要文字       Markdown 归档
键鼠空闲采样                                         （带缓存）             早晨弹窗
天气 API
```

**为什么要分层**：采集层的数据源会随时间增加（今天三个，明天五个），分析层的规则会被反复调整，呈现层要做多种形态。三层耦合在一起的话，加一个天气就得改报告生成逻辑。

### 分三期

| 期 | 内容 | 交付物 |
|---|---|---|
| **第 1 期** | 会话摘要（1~2 句 + 缓存）、工具统计、三层 HTML、明日待续 | 能用的日报 |
| **第 2 期** | 启停心跳、天气、近 7 天对比、成本与省钱建议 | 完整的日报 |
| **第 3 期** | 键鼠空闲采样、健康提醒、周报 / 月报 | 全功能 |

## 八、需要先拍板的三个问题

这三点决定了数据结构和隐私边界，先定再动手：

### 1. 隐私边界

会话正文要发给模型做摘要。选一个：
- **A**：接受用当前云端模型（效果最好，正文出本机）
- **B**：默认只用标题 + 统计，正文摘要设为可选开关（隐私优先）
- **C**：接本地模型做摘要（不出本机，但要额外配置与算力）

### 2. 键鼠采样能否接受

只记录「多久没动」，不记录按键内容、不截图、不上传。是否接受插件常驻做这件事？若不接受，健康板块退化为「只用 DSH 活动时间」，并明确标注为粗略估计。

### 3. 投递时机

- **固定时间**（如每天 09:00）：像传统日报，但关机期间会错过
- **每天首次打开 DSH 时生成**：更贴合「启停时间」的语义，不会错过，但看到报告的时间不固定

（可以两者并存：固定时间生成落盘 + 首次打开时展示。）
